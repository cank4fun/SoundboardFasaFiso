# Code signing and release verification policy

## Current status

Official SoundBoardFasaFiso portable builds are currently unsigned.

The project applied to the SignPath Foundation program at an early stage. The
application was not approved because the project does not yet have the level of
public adoption and independent visibility required by that program. The
project may reapply after it has broader community use. A paid certificate is
not planned at this stage, and missing code signing does not block development
or release publication.

Unsigned releases can trigger Microsoft Defender SmartScreen warnings, and
Windows application-control policies may block them. Users should not weaken
system security solely to run the application.

## Project roles

- Committer and reviewer: [cank4fun](https://github.com/cank4fun)
- Release approver: [cank4fun](https://github.com/cank4fun)

Changes submitted by contributors who do not have direct repository write
access must be reviewed before they are merged.

## Privacy policy

SoundBoardFasaFiso does not transfer user audio, microphone content,
configuration, logs, sound files or other personal information to external
systems.

The application contacts GitHub only when the user enables the optional startup
update check or manually requests an update check. The updater reads public
release information and does not upload user data.

The application does not automatically download, replace or execute updates.

## Official build and verification process

Official release binaries are built from the public source repository by
GitHub Actions on GitHub-hosted Windows runners. A release must correspond to a
public source commit and immutable release tag.

Each official portable ZIP is published with a `.sha256` file generated by the
same workflow. The checksum proves that a downloaded archive is byte-for-byte
identical to the release asset; it is not a substitute for an Authenticode
signature or publisher identity.

AEC-enabled releases use the pinned `vcpkg.json` manifest and include generated
license notices for WebRTC and all transitive static dependencies present in
the isolated manifest installation.

## Future signing

When a trusted signing path becomes available:

- only artifacts produced by the official repository workflow may be signed;
- every signing request must be manually approved by the release approver;
- the certificate and private key must not be stored in this repository or on
  maintainer computers;
- signed artifacts must still correspond to a public commit, tag and checksum.
